# Публикация Schola Clash

Сайт состоит из статических HTML/CSS/JavaScript. GitHub Pages размещает интерфейс, Supabase уже предоставляет базу и аккаунты. Отдельный сервер приложения не требуется. Эта инструкция подготовлена; сайт по ней ещё не опубликован.

## Что осталось до запуска

1. Подготовить зашифрованную резервную копию рабочей базы и проверить восстановление в отдельной пустой базе. Инструкция: [DEPLOYMENT.md](DEPLOYMENT.md). Реальное восстановление пока не проверено; локальный запуск age заблокирован Windows.
2. Проверить миграции в отдельном тестовом Supabase и согласовать применение к рабочей базе. Новые файлы применяются по порядку: `20261009070651_account_learning_reliability.sql`, затем `20261009163852_chapter_versioned_saves.sql`. Старые миграции не запускать повторно. Новый интерфейс требует обе новые миграции.
3. Настроить SMTP в Supabase и проверить письма подтверждения и восстановления на зарегистрированном тестовом аккаунте. HTTP 200 не подтверждает доставку. У ранее предоставленного email не было аккаунта; письма не пришли.
4. Настроить адрес сайта и разрешённые возвраты после подтверждения/восстановления.
5. Проверить ветку, дождаться успешного Checks и перенести готовые изменения в main. После этого включить публикацию.

## Как включить GitHub Pages

1. В репозитории `Kiliyas/Schola-Clash` открыть **Settings → Pages**. В **Build and deployment → Source** выбрать **GitHub Actions**. Для GitHub Free репозиторий должен быть публичным; для частного репозитория проверить доступность Pages в тарифе.
2. В **Settings → Secrets and variables → Actions → Variables** создать `SCHOLA_PAGES_ENABLED` со значением `true`, только после проверки и применения миграций. Это переменная, не пароль.
3. В **Settings → Environments → github-pages** при необходимости разрешить публикацию из `main`.
4. В **Actions → Publish website → Run workflow** выбрать `main` и запустить workflow. Он создаст папку `_site` и загрузит только десять файлов интерфейса и `.nojekyll`. SQL, тесты и административные скрипты в сайт не попадают. Автоматической публикации при каждом пуше нет.
5. После успешного workflow открыть адрес из deployment или **Settings → Pages → Visit site**. Ожидаемый стандартный адрес: `https://kiliyas.github.io/Schola-Clash/`. Точный адрес взять из Pages; собственный домен для размещения сайта необязателен.

Для локальной проверки пакета выполнить `node operations/build-site.cjs`. Результат находится в `_site`; эту папку не коммитить. Скрипт очищает только эту папку при повторной сборке.

## Настройки Supabase Auth

В **Authentication → URL Configuration** указать:

- **Site URL:** `https://kiliyas.github.io/Schola-Clash/` — либо фактический адрес Pages, если он отличается.
- **Redirect URLs:** `https://kiliyas.github.io/Schola-Clash/` и `https://kiliyas.github.io/Schola-Clash/index.html`.
- Для разработки отдельно добавить используемые локальные адреса, например `http://localhost:8000/` и `http://127.0.0.1:8000/`.

При переходе на собственный домен заменить Site URL и добавить точные новые Redirect URLs. Не использовать широкие маски для рабочего сайта. Проверить шаблоны писем: ссылки должны учитывать настроенный RedirectTo. После перехода по письму пользователь должен возвращаться в приложение.

В **Authentication → Email → SMTP settings** включить свой SMTP и заполнить host, port, username, password, From email и имя отправителя по инструкции выбранного почтового сервиса. Подтвердить отправителя/домен и DNS записи, которые потребует сервис. Встроенная почта Supabase ограничена адресами участников команды и не предназначена для обычных пользователей рабочего приложения. SMTP пароль хранится в Supabase, а не в JavaScript или GitHub Pages.

`supabase/client-config.js` содержит публичный publishable key: он предназначен для браузера. Администраторские ключи и пароль базы туда добавлять нельзя. Доступ к данным защищают политики RLS и проверки RPC.

## Проверка опубликованного сайта

- Зарегистрироваться с новым email, получить письмо и подтвердить аккаунт.
- Запросить восстановление, открыть полученную ссылку, изменить пароль и войти с новым паролем.
- Учителем создать класс, выдать код; учеником войти в класс и увидеть только назначенные главы.
- Проверить редактирование главы, конфликт двух вкладок, практику и отдельное повторение ошибок.
- Провести дуэль двумя тестовыми аккаунтами; сверить результат и рейтинг на обеих сторонах.
- Проверить телефон и отсутствие ошибок JavaScript. Убедиться, что нет ошибок отсутствующих колонок/RPC: они означают неправильный порядок развёртывания.

Это техническая проверка запуска, не исключённый пользователем школьный пилот. Для эксплуатации также нужен ответственный администратор запросов учителей/удаления и настроенные резервные копии. Автоматические операции включаются отдельно, по DEPLOYMENT.md.

## Откат

Если новый интерфейс работает неправильно, вернуть проверенную версию файлов в main и вручную повторить Publish website. Миграции и новые таблицы не удалять ради отката интерфейса. При откате до `480e71a` новый RPC проверки версии не используется: защита от конфликта требует актуального интерфейса. Восстановление данных выполняется отдельно и не проверяется поверх рабочей базы.

Официальные инструкции: [GitHub Pages workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [Supabase Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls), [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp).
